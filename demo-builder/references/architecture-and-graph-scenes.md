# Architecture And Graph Scenes

Use this reference for architecture diagrams, knowledge graphs, process networks, progressive disclosure, complex connector systems, or metaphors that transform raw inputs into structured knowledge.

## Reading Order

1. Choose the semantic transformation.
2. Reserve layout lanes and inspector space.
3. Place fixed node geometry.
4. Route and validate structural links.
5. Add semantic highlights and cue transitions.
6. Capture settle and event-boundary frames.

## Make The Mechanism Visible

Translate abstract narration into a causal visual transformation. Prefer:

```text
raw inputs → governed refinement → durable structure → connected model → decision path
```

Examples include documents becoming particles that fill a page-shaped mold, scattered records resolving into an index, or a compact network expanding into a full graph. A metaphor must preserve the actual technical boundary: do not imply model training, authority, or automatic learning when the system only indexes, retrieves, proposes, or awaits approval.

When current and future capabilities coexist, reserve a stable truth lane for labels such as `TODAY`, `DEMONSTRATED`, and `NEXT`.

## Architecture Layout

- Use fixed source, reasoning/process, and result lanes before creating objects.
- Use opaque cards and border ports. Never draw a production connector from center to center through card text.
- Prefer orthogonal routes for process and system architecture.
- Give every connector route metadata so scene assertions can test clearance.
- Route first, then place relationship labels in dedicated empty gutters.
- Keep labels out of connector paths; never use a bordered label whose outline reads as another edge.
- Split a complex architecture into cue-revealed layers rather than showing every connector immediately.

## Knowledge-Graph Layout

- Use a planar or near-planar layout when the graph is explanatory rather than exploratory.
- Keep node labels inside fixed opaque cards. This allows links to pass behind nodes without crossing readable text.
- Clip straight links to node borders and render structural links below node z-order.
- Use thin, dim links for network context. Use brighter overlays only for the relationship being explained.
- Avoid arrowheads on the base network. Show direction through animated pulses, a semantic inspector, or carefully placed highlighted arrows.
- Limit the visible graph to the smallest network that proves interconnection. Nine nodes and roughly sixteen planar links is often enough for a central decision neighborhood.
- Put relationship semantics in a dedicated inspector lane, for example:

```text
EVIDENCE SUPPORTS · POLICY CONSTRAINS
DECISION → ACTION → OUTCOME · SOURCE RECEIPT
```

- Show progressive disclosure by dimming irrelevant nodes and links while keeping the relevant neighborhood at full opacity. Do not delete context unless the narration says it is absent.

## Graph Build Sequence

A robust cue sequence is:

1. Show source material.
2. Show authorization or governance boundary.
3. Animate refinement without drawing a line through labels.
4. Settle on a durable page/index/record structure.
5. Move that structure aside and reveal a compact graph.
6. Remove the old structure before expanding the graph.
7. Explain node and edge anatomy.
8. Highlight evidence and policy relationships.
9. Extend the path through decision, action, and outcome.
10. Show current/future truth boundaries.
11. Pulse validated history through the graph.
12. Settle on the relevant decision neighborhood.

Use cue `focus` boundaries to sequence removals and introductions. If two text-bearing groups occupy the same lane, fade the first group completely before revealing the second.

## Training And Feedback Loops

Distinguish these concepts visually and verbally:

- **Initial grounding**: authorized history is classified and connected.
- **Graph refinement**: validated relationships, conditions, or precedents are added or strengthened.
- **Model training**: model weights or learned parameters change.
- **Runtime retrieval**: the worker opens a relevant neighborhood without changing the graph.

Human feedback should normally enter as candidate evidence. Show review, evaluation, approval, versioning, and reversibility before it changes a governed graph or worker. Never animate a human answer as an immediate silent rewrite unless that is confirmed system behavior.

## Connector QA

For every final or cue-boundary state:

- confirm links start and end at intended node borders
- confirm no link enters an unrelated node or text container
- confirm independent orthogonal routes do not cross or share a run
- confirm highlighted paths remain legible over base links
- confirm markers and source receipts sit outside node text
- confirm inspector labels do not overlap bottom nodes, badges, or truth lanes

Base-network crossings may be acceptable only when unavoidable and visually unambiguous. Prefer a planar layout before accepting crossings.

## Transition QA

Inspect onset, focus, land, and settle frames for:

- two labels crossfading in one lane
- a moving page or panel passing through fading text
- particles settling on top of node labels
- connectors appearing before their endpoint nodes
- graph expansion intersecting a still-visible source panel
- a final pulse, trail, or temporary label persisting into settle
